# M3 owned browser operations: private input and execution boundary

This is a **prepared entrypoint, NOT_RUN**. Preparing this entrypoint starts no API, Web, Worker, PG or browser; an authorized execution launches a Playwright-managed browser. Root must approve the exact new owned window, combined source/build, synthetic records, real POST counts and response-loss injection before execution. Existing `playwright.m3.live.config.ts` and its read-only test remain separate.

Root supplies an absolute owned 0700 private directory; `window.json` and `m3-browser-seed.json` are regular files owned by the current OS user with mode 0600 (no symlinks). No secrets go in the repository, commands, output, screenshots, traces or videos. `window.json` has the existing `source_sha`, `build_id`, `web_origin`, `api_origin`, `web_pid`, `api_pid`, `stop_at_utc` fields; origins and current listener owners must pass `ownedEndpoints` and `readOwnedListener`. `source_sha` must equal the **actual combined checkout HEAD**, and `build_id` its `.next/BUILD_ID`. Window requires two distinct Web/API origins and listener PIDs, a clean combined checkout and at least 120 seconds initially; all requests stop at `stop_at_utc - 90s`, listener/build/source/clean-tree checks repeat before each API request, and the context closes at that point. Root separately owns all process/PG cleanup and must reserve enough time for it.

`m3-browser-seed.json` is an object with these exact required facts (placeholder names below are descriptions, not executable values):

- `organization_id`: the new owned organization UUID, matched to each real login and Copy candidate scope.
- `daily_shop_id` and `inquiry_shop_id`: distinct new owned shop UUIDs within the same organization. The first is bound to the daily/Taipei source; the second to the Mock demo/Shanghai source. Copy uses `copy.shop_id`, which must equal `inquiry_shop_id`; never substitute one UUID for the other.
- `owner`, `reviewer`, `unassigned`, `outside`: separate `{login,password,home_path,principal_id,shop_roles}` objects. `home_path` is the actual `/tasks` or `/access` returned by the session; `shop_roles` is an object keyed by **both exact shop UUIDs**, each mapping to an array of actual `operator` and/or `approver` grants (use an empty array where none). The same owner has operator on both; reviewer and unassigned each have approver on the Copy shop, outside is an operator on the daily shop with `/tasks` home (to satisfy the shared middleware) and has neither role on the Copy shop; all four principals differ. The reviewer is the explicitly assigned candidate reviewer. Each successful login's returned principal and grants must match. No role escalation is performed.
- `daily`: `{day,timezone,source_version,metric_key,minimum_evidence}`, with `timezone` exactly `Asia/Taipei`. The date and source version must be currently enabled for the daily shop, the selected metric must support `metric_evidence`, and this synthetic report must yield at least `minimum_evidence >= 51` citations so actual evidence pagination is exercised.
- `inquiry`: `{question,sku,expected_value}`: an actual supported inquiry and an exact string fact expected from the fixed synthetic Mock deployment on `inquiry_shop_id`. No test route provides API results.
- `copy`: `{shop_id,registry_id,registry_digest,product_source_id,query_ref,reviewer_id}`: already owner-registered **synthetic** source identifiers and a server-owned pinned, versioned query ref; `reviewer_id` equals the reviewer account's principal. Root must separately provide and pin the backend deployment/loader and configure the actual API wiring.
- `max_poll`: integer 1–30; `acknowledge_lost_response`: literal `true`. The latter explicitly confirms that each of the seven authorized POSTs below will be sent once and its real response discarded. Without it this entrypoint refuses to run.

Seven real business POSTs are planned: one daily report, one daily question, one inquiry, two distinct Copy candidates and two Copy review decisions: **seven** in total. The explicit approval and capacity must cover all seven; there are no automated POST retries. Each uses the product UI; Copy create preview and the actual POST body are independently checked against every private seed source/reviewer field and the frozen DTO before one-shot, exact-method/path/query/body network authorization. The inquiry key is generated during the POST and captured only if the whole synthetic input matches. One-shot Copy capability probes accept only `/api/v1/copy/candidate-requests/{UUID}`. Context-wide routing aborts every unpermitted request, blocks service workers and WebSockets, and never calls `route.fulfill`.

For each POST the guard durably fsyncs the original request and key to a newly created, exclusive 0600 `m3-operations-ledger.jsonl` **before network forwarding**. The interception forwards exactly one real request using `route.fetch({maxRetries: 0, maxRedirects: 0})`, discards its response with `route.abort`, then tests that the visible UNKNOWN state resolves through the original-key GET. A network error or nonexpected real status fails and stops; it does not retry or claim rollback. The ledger records intent, forwarding, observed status, received original-key receipts and final test statuses; passwords, cookies, CSRF tokens and response bodies are not logged. Reusing the same private directory with an existing ledger fails closed.

The three bounded tests exercise report → receipt → same report → question → receipt → evidence pagination, inquiry original-key and task reads, and two candidates with assigned reviewer approve/reject plus owner draft and denied unassigned/out-of-scope reads. UI assertions use 390px and check feedback and clipping. Candidate read-back does not independently prove the original `query_ref`, because the frozen response does not return it. A passing 390px run does not prove other viewports or external send.

Invocation is intentionally not a service launcher: in the registered window and combined checkout, Root may set `COMMERCEOPS_M3_LIVE_WEB_URL` to its exact Web origin and `COMMERCEOPS_M3_PRIVATE_DIR` to the private directory, then run the locked toolchain's Playwright with `--config playwright.m3.operations.live.config.ts`. The config has one worker, zero retries, `maxFailures=1`, no traces/video/screenshots and a bounded timeout; outcomes remain NOT_RUN until the authorized real run. On any failure retain the ledger and report actual statuses, including UNKNOWN and unexecuted cases; do not re-run without new authorization.
