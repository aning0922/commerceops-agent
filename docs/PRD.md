# 产品需求 PRD

日期：2026-10-08（Asia/Shanghai）。状态：首次外部审核有条件通过，本稿落实审核修订，等待最终确认。本文的指标为拟定验收目标，并非已取得的测试结果。

## 1. 定位与业务价值

CommerceOps Agent 帮助小型电商运营团队将“查数—分析—建议—审批—跟进”变为可追溯的业务流程。用户通过飞书或 Web 下达自然语言请求，系统用确定性计算产生事实，以 LLM 组织解释，以人工授权控制执行。

求职展示应能解释：为何选择工作流、状态如何持久化、重复事件为何不产生重复任务、审批如何绑定数据、外部接口失败如何恢复，以及模型输出如何被事实约束。作品不以工具数量或多 Agent 数量评价。

第一版范围：一个组织、一个店铺、少量授权用户；建议容量基线为 5 名用户、1,000 个 SKU、查询窗口内 10,000 条订单行。Phase 1 起至首个可面试版本采用单 Worker、全局单 Graph 执行并发，其余分析任务持久排队；API/Gateway 仍可接收请求。超出数据容量要明确提示，不静默截断数据。

首个可面试版本（M1）以“库存 Agent + 真实飞书审批”为第一交付目标，使用 MockCommerce，包含内部补货项创建/完成/关闭、Base 同步、恢复证据和最小 Web 轨迹。完整 P0（M2）补齐 Woo 只读测试店与完整交付验证；完整求职版本（M3）再加入 P1 日报、受限动态只读 Tool 查询与 RAG 文案草稿。三者范围、工期及验收映射以 [ROADMAP](ROADMAP.md) 为准，不能将 M1 宣传为全部功能完成。

## 2. 用户及权限

| 角色 | 能力 | 限制 |
|---|---|---|
| 运营 operator | 创建分析、查看授权任务、提出重算 | 不能通过自然语言批准执行 |
| 审批人 approver | 查看冻结建议，批准或拒绝；完成/关闭同店铺内部补货项 | 审批绑定具体版本；关闭须有原因，不代表真实入库 |
| 管理员 admin | 配置允许用户、规则与集成，处理异常 | 不默认获得业务审批权，需显式分配 approver |

角色可兼任以支持个人演示，但验收必须包含另一个无权限身份。所有 UI/API/飞书动作复用同一服务端授权逻辑。第一版不建设组织树与通用 RBAC 平台。

## 3. P0 用户旅程

请求示例：“分析最近七天的商品销量和库存情况，找出可能缺货的商品，生成补货建议。”

1. 校验组织、用户、群聊范围与 @ 目标，持久化事件和业务任务，返回任务编号。
2. 解析时间范围与商品范围。默认“最近七天”为店铺时区最近七个完整自然日，当前日不参与销量统计；卡片同时注明库存查询时点。例如 10 月 8 日发起，销量窗口为 `[10-01 00:00, 10-08 00:00)`。
3. 查询并冻结商品、订单行、退款和库存快照。空数据与查询失败分开处理；部分分页失败不能标记为完整。
4. 确定性计算日均需求、可用库存、风险级别和补货建议。展示参数、数据来源、数据新鲜度及异常。
5. LLM 依据结构化事实撰写简明报告。数值表格由程序渲染；LLM 不决定数量、权限或执行结果。
6. 存储不可变计划版本，发送包含明确 SKU、数量、风险、参数和有效期的审批卡片。默认最多 20 个可执行条目；超出时先让用户缩小范围，不悄悄只批准前 20 个。
7. 审批人明确批准或拒绝；在途未知时必须使用第 4.1 节的显式假设确认动作。批准不等于已执行；执行前再次检查权限、有效期、建议版本、确认记录、库存与已有未关闭补货任务。
8. 条件满足时，在一个数据库事务内幂等创建内部补货任务及发送记录。
9. 异步同步至飞书多维表格，发送结果；记录全程业务审计、工具调用和模型用量。

**补货任务**是供运营跟进的工作项，含 SKU、建议数量、依据、审批人及状态。它不是 WooCommerce 订单，不增加真实库存，不代表采购合同、采购付款或商品已入库。

## 4. 库存规则 v1

详细数据口径见 [电商契约](COMMERCE_INTEGRATION.md)。规则参数按店铺设置，可提供 SKU 覆盖；默认样例参数必须标注“演示假设”：采购提前期 L=3 天、复查周期 R=7 天、安全天数 S=2 天。

- `D = window_gross_demand_units / 7`。v1 用窗口内有效订单的原始成交件数估计需求，退款件数独立展示，不将退款金额换算成件数，也不假定退款已回库。
- `A = adapter_available_stock`。保留负库存为欠货信息；未知库存不是零。
- `T = ceil(D × (L + R + S))`；风险触发线为 `D × (L + S)`。
- D>0 且 A≤0：缺货；0<A≤触发线：补货风险；A>触发线：正常。D=0 且 A>0：无近期需求，不自动补货；D=0 且 A≤0：人工检查，不能凭空推导数量。
- 对可执行的风险 SKU：`Q = max(0, T − A − effective_inbound_units)`。有可靠在途数据时 effective_inbound_units 等于来源 inbound_units；未知时保留来源 null，effective 取 0，只输出“在途未知、按 0 估算”的草案，必须通过第 4.1 节显式确认后才能执行；不能伪称完整供应链预测。
- 默认不启用 MOQ、包装取整、供应商择优、促销预测。若业务确需新增，必须以规则版本、字段和测试共同引入。
- 有未关闭内部补货任务的 SKU 不再自动创建第二项；展示已有任务并要求先核对，不能当作可靠在途库存扣减。

示例：7 天 70 件，D=10，A=20，在途确认 0，L=3/R=7/S=2。目标 120 件、触发线 50 件、建议 100 件，覆盖天数 2 天。零销量、未知库存、负库存分别有独立验收用例。

风险结果包含 `eligible_for_execution` 和 `quality_flags`；执行资格由服务端结合审批的 `acknowledged_assumption_keys` 计算，不接收客户端的资格布尔值。缺失数量、无法判定的共享库存、来源不完整的条目不得进入审批执行清单。低质量样本可生成说明报告，不伪造正常结果。

### 4.1 在途未知的显式确认合同

仅“在途未知、估算为 0”可按此流程人工接受，不能用它豁免库存数量缺失或数据不完整。原始 `inbound_units=null` 始终保留，计算使用 `effective_inbound_units=0`，不得在确认后改写成“已确认在途为零”。

1. 服务端为每个受影响 SKU 生成假设键 `inbound_unknown_zero:{sku_key}`，与假设类型、估算值 0、说明版本一起写入冻结计划。完整假设集合及其 SKU 范围进入 plan_hash。
2. 卡片逐项列出受影响 SKU，说明“在途未知，按 0 估算可能造成重复补货；批准仅创建内部工作项”。只提供明确的 **“确认在途未知按 0 估算并批准本版本”**（`approve_with_assumptions`）和 **“拒绝此假设并拒绝计划”**（`reject_assumptions`）动作；不提供默认勾选或以普通“同意”代替确认。
3. 确认与批准是同一次显式点击、同一事务落库，不另存可跨人/跨版本复用的临时确认。请求包含 approval_id、plan_id、plan_version、plan_hash、action、acknowledged_assumption_keys、nonce。操作者从可信平台回调/会话取得。
4. 服务端校验身份/角色/店铺、当前 pending 审批、计划版本/hash、有效期、nonce 和数据质量。确认键集合必须与数据库计划要求完全相同，不能漏项、加项或只信任客户端 `true`；普通 `approve` 遇到未知在途返回 `ASSUMPTION_ACK_REQUIRED`，审批仍 pending，不入执行队列。
5. 通过后原子保存决定、确认键、操作者、时间、来源事件和 resume job。拒绝动作不要求确认键，记录 `INBOUND_ASSUMPTION_DECLINED` 并置 rejected，补货项为 0；未点击或关闭卡片不等于拒绝，也不等于同意。
6. 同一操作者对同一版本的相同有效动作重复提交返回原决定，不重复写确认/决定审计或 resume job；新操作者、相反动作或不同确认集合返回已决定/冲突。同意后不能用拒绝回滚历史。已生效决定的重复查询不重新执行，过期后也只返回既有结果。
7. 新版本、新 SKU 范围、数量/假设/在途事实变化均需重新审批，旧确认不继承。执行前复核确认键与该计划 hash 仍匹配；在途变为已知值即使数量巧合未变，也属于假设变化。

### 4.2 内部补货项的最小业务周期

Phase 3 规划一个受鉴权 Web/API 操作：同店铺 approver 对指定 item_id 将 `open → completed`（内部跟进完成）或 `open → closed`（取消/无需继续），必须填写原因。admin 不自动有权，需兼任 approver。只处理一个条目，不做批量、重新打开或真实采购/库存修改。

状态转换、操作者/时间/原因、版本更新、审计和 Base 投影 outbox 同事务保存。相同请求键与 payload 重试返回原结果；不同请求对终态返回冲突。终态释放该库存池的 active 唯一约束，下一轮必须新建分析任务、重新采集并审批；不能重放旧执行来新建条目。完成/关闭不改变原分析任务的 completed 结果，也不证明商品已入库。

## 5. 功能边界

| 优先级 | 包含 | 本阶段不承诺 |
|---|---|---|
| P0 / M1 | Mock 数据、真实飞书消息/卡片、显式假设确认、审批拒绝与恢复、内部补货项创建/完成/关闭、Bitable 同步、最小 Web 与审计 | 真实采购、修改 Woo 库存、退款/支付、ERP、供应商管理 |
| P0 后段 | Woo 测试店只读适配；精简 Web 任务/审批/轨迹页 | 通用 BI、实时库存预留、全渠道库存合并 |
| P1 日报 | 订单/退款指标、异常规则、证据追问、持久定时执行与推送 | 由模型自由写 SQL；把毛收入宣称为利润 |
| P1 只读 Agent 展示 | 根据意图选择/组合白名单查询 Tool，保留调用轨迹与证据 | 通用规划器、多 Agent、自主写操作；不阻塞 M1 |
| P1 文案 | 商品与 SOP 检索、引用、候选文案、人工审核后保存内部草稿 | 直接发布商品、自动改价格、未经授权抓取外部资料 |
| P2 | 企业微信/钉钉、国内平台、官方审批中心、MCP、平台对比、多 Agent 研究 | 为这些扩展提前引入复杂基础设施 |

P0 支持澄清参数、查询同一任务进度及解释已有结论；丰富的日报跨轮分析在 P1。群聊上下文按“组织+聊天+发起人+话题/显式任务”隔离，不能让其他群成员消息改变待审批计划。

## 6. 状态与异常体验

展示分析中、待审批、已拒绝、已过期、需重新审批、内部执行完成、同步待恢复、失败需处理。批准回调只回复“审批意见已记录/处理中”；拒绝回复“已拒绝，不创建补货项”，重复动作显示既有决定。不在接收成功时宣布补货成功。

重复事件返回原任务；重复同意返回原决定；同意后再拒绝返回冲突并显示已生效决定。审批过期、计划变化、角色撤销阻止执行。重试操作沿用原任务及逻辑幂等键；“重新分析”明确产生新版本，旧版本失效。

## 7. P0 交付验收

| 编号 | 验收条件 |
|---|---|
| AC01 | 在飞书私聊和群 @ 中各完成一次完整闭环；能查到 PG 任务、审批、补货及表格记录 |
| AC02 | 固定数据集的销量、风险、数量与黄金结果完全一致；LLM 改写不改变事实 |
| AC03 | 审批拒绝后补货项为 0；拒绝与同意并发时仅一个决定生效 |
| AC04 | 同一事件/审批重复 10 次、Worker 在提交边界被终止并重启，内部补货项仍各只有一条 |
| AC05 | 未授权、跨组织、篡改 plan_hash、过期审批和权限撤销不能执行 |
| AC06 | 外部超时、429/5xx、同步失败均有可见状态及恢复；未知写入结果不盲目重发 |
| AC07 | 待审批状态可跨进程重启恢复，不依赖内存会话；过早审批也不丢失 |
| AC08 | Compose 从干净环境复现离线闭环；真实飞书与 Woo 分别有明确联调证据 |
| AC09 | 单次运行可查询数据来源、规则版本、模型版本/Token/耗时、工具步骤与审批证据 |
| AC10 | 未知在途只能以绑定本版本的显式确认批准；漏确认/篡改/跨版本不能执行，拒绝为零补货，重复确认只产生一个决定 |
| AC11 | 有权用户完成/关闭内部补货项，留下原因和审计；重复请求幂等；同 SKU 下一轮经新分析与审批可创建，旧执行重放不新建 |

M1 要求 AC01–07、AC09–11，以及 AC08 的干净环境离线复现和真实飞书证据；AC08 的 Woo 真实证据在 M2 补齐。M2 才算完整 P0，M3 的 P1 评测见 TEST_PLAN。首次外部审核中的“P0 必须修订 / P1 建议调整”是审核优先级，不改变此处的产品 P0/P1 命名。

性能目标：入站本地持久化处理 p95<1 秒，满足飞书 3 秒限制；离线受控分析执行 p95<10 秒，真实模型分析执行目标<60 秒（不含排队、人工等待及外部故障）。排队耗时单独记录；恢复扫描调度目标≤30 秒，单 Worker 忙时下一调度点处理并报告延迟。以上需在标注机器与数据规模的测试报告中验证，不能作为供应商 SLA。
