## 2. 可信身份与入站 T1

正式入口另命名，锁定 lark-oapi 1.7.3，只注册 `im.message.receive_v1` 与新版 `card.action.trigger`；不开放 HTTP 未鉴权入口。SDK 鉴权后的回调 envelope 必须匹配应用与租户。消息只接受 human sender、允许用户、私聊或唯一允许群且 mentions 包含真实 bot open_id；拒绝 bot、非 @、其他类型与跨租户。上限 32768 bytes/4000 字符/100 mentions，不回显输入或 SDK 原文。

平台 actor 来自 `(app_id, tenant_key, operator.open_id)` → 当前 PG `identities(provider='feishu')` → principal，不读按钮中的 actor/roles/scope。正式 `FeishuActor` 与 `WebActor` 分支均在业务锁后复核 enabled/auth_version/当前组织店铺角色及身份映射；飞书分支不创建 Web session。PG 权限函数保留原 Web 分支，增量支持明确组织应用租户绑定的 Feishu 分支。admin 不隐含 approver。

T1 在同一 PG 短事务写 durable inbox、逻辑 message 去重、会话、全新 P3 `inventory_replenishment` 任务及新周期所需 source task/job/audit；不复活 P2 completed。event_id 与 message_id 去重分层，同原 message 新 event 返回原 task，同键异身份/内容拒绝。会话按组织/聊天/发起人/明确 topic 隔离。只保存必要标识/规范化请求/hash，不保存原始 SDK payload。数据库提交成功后才返回 handler；DB 异常传播失败，不能先 ACK 后落库。

首批入口使用显式固定演示规则与有界确定性请求文法；模糊/不支持请求返回需澄清，不调用真实模型、不凭自然语言批准。source/model/approval_mode 标识各层真实范围；SDK Fake 与 simulated_feishu 不记 human_feishu。

## 3. T2/ready、卡片意图与 T3

复用 P3 工作流版本、单 Worker/全局单 Graph、T2 冻结计划和唯一人工 interrupt。T2 原事务生成 card outbox 且 blocked；持久 checkpoint 被协调器核验到当前 task/plan/approval/唯一 interrupt 后才持久 ready_at 并发布 pending。R05/R06 间隙无先发卡；重启不新建计划/意图。

JSON 2.0 完整披露最多 20 SKU、数量/风险、来源/窗口/观测时点、L/R/S、版本/hash、期限及完整 required_assumptions，不截断为 top-N。未知在途仅专用 `approve_with_assumptions`/`reject_assumptions`；value 仅 approval_id、plan_id/version/hash、action、acknowledged_assumption_keys、nonce。无未知时普通 approve/reject；按钮中不传执行数量、actor 或资格布尔值。

callback 校验可信 operator、当前组织/店铺角色、eligible、持久发送绑定 chat/message、plan/version/hash、nonce、锁后 DB 时钟/有效期与完整精确假设集合，然后调用与 Web 共用的 P3 T3。决定/确认/audit/原请求回执/resume job/入站回执同事务；原 source `feishu` 可追溯。重复同 actor/同语义返回原决定，其他 actor/相反动作/异集合冲突，不覆盖历史。重复请求仍校验身份、nonce 和版本；原决定不重新执行。T4 仍独立检查持久授权/当前角色/期限/新观测，不改变 P3 原恢复规则。

Toast 仅报告“审批意见已记录，等待执行”/“已拒绝，不创建补货项”/“已有决定”或固定失败码；不把 T3 受理声明为内部执行完成。回调 token 不作恢复凭据。异步结果来自 PG 实际业务状态和原 execution；卡片更新失败不回滚审批。

## 4. 共享 DTO 与 B 接口

首审[Review5481706893](https://github.com/aning0922/commerceops-agent/pull/43#pullrequestreview-5481706893)精确d75有P1（request/result缺机器绑定），原26独立offline/type/docs/scan通过不抵该阻断；f507仅null修正不消除此P1。本候选增补唯一绑定校验与负例，Root复审及当前精确CI仍待；首CI38107482765仅绑定d75，历史保留。

机器合同：[contracts.py](../../backend/src/commerceops/application/feishu_business/contracts.py)。B 在 `projection_contract.py` 从此共享模块导入或显式 re-export `ItemProjection`、`ProjectionRequest`、`ProjectionResult`、`BaseProjectionAdapter`，不要复制另一份 outbox DTO。

唯一接口：`async project(request: ProjectionRequest) -> ProjectionResult`。A 提供 outbox_id/org/shop、受信 target_key、operation=create/update/reconcile、持久 UUIDv4 client_token、原 external_id、完整 immutable ItemProjection、timeout_seconds≤10（整个operation含完整分页的绝对总deadline，不逐页重置）/max_pages≤100。target_key 是私有配置中测试表别名；app_token/table_id 不进入共享 DTO、日志或 GitHub。B 不自行重试/新键/新增消费者；SDK transport 单次有界操作后做完整读回，分页到限或缺页返回 unknown/fatal，不把部分页视为完整。

ItemProjection 映射固定 15 列：CommerceOpsItemID/TaskID/SKU/Quantity/Risk/Window/SourceMode/ApprovalStatus/ApprovedBy/BusinessStatus/ResolutionReason/ResolvedBy/ResolvedAt/SyncVersion/UpdatedAt。金额/数量/状态由 PG 确定。版本≥1，open 的终态三字段全null，completed/closed 三字段齐备，时间带时区。名称和日期用文本，不增加人员/附件权限。DTO fields() 输出完整列，终态空值显式null；update是增量写，不能用空字符串假定清除。完整读回仅允许对已核schema中的这些nullable列将远端显式null/空文本归一为None；当前必须完整15键，省略任意键一律unknown，不根据无证据的省略假设标verified；旧非空残值必须不匹配，不把它归一为空。

| outcome | 必需证据/意义 | A 唯一持久映射 |
|---|---|---|
| verified | complete=true、matched_count=1、content_matches=true、external_id 与 observed_version 齐备；A 再核版本 | 原意图 sent + 原 item 映射，无业务回滚 |
| retryable | 供应商具体错误合同/完整读回明确无写入，write_rejected=true；可含1–300秒延期 | retry_wait，最多3次，原键原内容；unknown 不能因此回 pending |
| unknown | 写请求5xx/timeout/ACK丢失或429/code/冲突未能证明明确拒绝；分页不完整/查找零条/内容不符 | unknown，后续只 reconcile，不盲 create/update |
| conflict | 完整原键查询多条、记录归属冲突 | dead/needs_attention，人工核对 |
| fatal | 身份/配置/字段/明确永久错误 | dead，固定分类，不泄露响应原文 |
| stale | 远端或当前 PG 更高版本，旧意图不可写回 | dead/STALE_PROJECTION分类，原键及历史保留 |

写请求不能仅按HTTP状态判retryable：5xx/超时/ACK丢失可能已经成功，默认unknown/reconcile；429或业务写冲突仅在供应商具体合同/读回证明明确拒绝且无写入时write_rejected=true。unknown意图即使后来收到retryable也保持unknown，只对账，不回pending。一次operation总deadline含所有分页/读回，方法计数、总次数cap及绝对测试窗口另外硬限制。

A/B必须统一调用共享唯一 `bind_projection_result(request, result)`；B返回前调用，A持久写sent前再次调用，不复制校验器。result.observed_fields须实际读回完整15键并与request.projection.fields()按唯一normalize_projection_fields比较；observed_version必须严格等于request版本，update或已有external_id的reconcile须严格匹配原record。较低版本/内容不符/缺键归unknown，较高版本归stale（禁写），错误record归conflict，不能只信任content_matches布尔。

verified 必须包含所有 15 列完整读回且等于目标版本与内容，不能仅凭 HTTP200/code0。update 必须有已持久 external_id；create 不得已有 external_id。unknown 先完整 CommerceOpsItemID 查询：恰好一条且完整内容版本匹配才 verified；零/多/不完整/不符停。未知 token 长期保留期限不作假设，不换 token 重新建行。旧版本不覆盖新版本；同 target table 串行写由 A 唯一 Worker 协调。B 只给事实分类，不决定业务终态或重启任务。

## 5. outbox、IM 窗口与限额

A 使用已有 outbox/内部业务事务和单 Worker，持久保存稳定 aggregate/version、request_hash、UUIDv4 provider key、attempts/next_attempt_at、结果与映射。发送前短事务领取并持久 sending，网络不持业务长事务；重启将无法证明 ACK 的 sending 变 unknown。任何进程失锁停止外发，旧进程确认终止前不启动替代消费者。

P3 旧 mock/controlled_stub 的禁发及未知约束保留；P4 正式意图须独立持久绑定并检查明确 sender gate，不把旧 probe/旧 mock 意图自动升级实发。准备与实际平台调用分离，默认 sender disabled，受控窗口才启用。限额一次最多20业务SKU、transport≤10s、最多3尝试、延期1–300s、分页≤100；总窗口绝对截止不重置，cap按实际调用方法计数，含失败。

IM 原 UUID 在发送前持久化，首 attempt 时钟起算3600秒：unknown 仅在已核同原键去重窗口内按明确恢复合同处理，超过或等于1h必须 needs_attention/安全对账，无自动新键盲发。未得到真实 message_id 不标 sent；任何新结果消息是明确新意图，不能伪作原发送重试。Base unknown 与 IM unknown 区分，两者均不回滚内部完成/关闭或重执行 T4。
