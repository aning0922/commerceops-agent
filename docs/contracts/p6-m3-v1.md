## 2. 日报数据与统计口径：`daily-metrics-v1`

### 2.1 时间、来源及覆盖

日报业务日 B 为店铺 IANA 时区的完整自然日，窗口为 `[B当地00:00,(B+1)当地00:00)`，
分别换算 UTC，不用固定 24 小时推导 DST 日。手动默认最近一个完整日；请求可显式选一个已结束日，
不得查询未来/当前未结束日。v1 最早允许日期由服务端来源能力给出，不能凭“30天”读工具预算推定覆盖。
测试注入冻结 clock；运行中采用可信服务端/DB clock，客户端不指定 now/UTC 边界/时区/币种。

新日报输入必须含**订单头全集发现证明**，包括无商品行订单；按 paid_at/created_at 分别裁剪。
跨期退款按 refund occurred_at 裁剪，须发现早于 B 创建、早于 B 支付订单的当日退款。
第一 Woo 候选采用有界全店订单头扫描，再读取这些订单的全部退款；本地筛选支付/退款日。
不能以 B 的创建时间订单 cohort、已有商品行集合或七日库存 snapshot 作为全店发现范围。
来源若不能完整枚举相关订单及其退款（包括已不可访问订单），须明确 `coverage_unproven`；
仅有“端点返回空列表”不足以证明当日零退款。替身必须显式声明其完整 fixture 范围。

扫描复用只读 transport 与 TLS/原点/分页/容量/同步 I/O 总截止保护，边界由新版本配置显式给出。
超过限额、分页变化/重复/遗漏、币种冲突、未知状态映射、非法金额/时间或部分请求失败，
均不提交完整日报。保存安全诊断与质量原因；不得将部分 totals 当全天数据，或静默删坏订单。
多请求仅为 `consistency=observational`；保存采集起止、覆盖策略/范围/计数和验证结果，不称原子快照。
本合同不依赖未验证的 Woo paid-date/refund-date 服务端过滤或增量游标能力。

### 2.2 指标、金额组成与空值

所有金额同币种、Decimal/`numeric(20,6)` 可表示；拒绝 float、bool 金额、NaN 及隐式舍入。
一个报告只允许冻结店铺币种，不做汇率转换或跨币种求和。JSON 用规范十进制字符串。
聚合须精确且不依赖进程全局 Decimal precision；任何输入或合计越 numeric(20,6) 范围均拒绝，不截断或溢出后继续。

| 字段 | 精确口径 |
|---|---|
| `created_order_count` | 订单头中 created_at 在 B 的 distinct order_id 数，覆盖所有已识别状态；另列 status_counts，不叫有效销售或支付订单数 |
| `paid_order_count` | 源明确记录 paid_at 在 B 的 distinct order_id 数；订单创建日不限制，后续取消/退款不反向抹除该次已记录支付 |
| `paid_product_net` | 上述支付订单的原商品行折扣后未税 net_amount 合计；不重复减 coupon，不扣退款，不叫利润 |
| `paid_product_tax` | 同 cohort 商品行税额合计 |
| `paid_shipping_net` / `paid_shipping_tax` | 同 cohort 订单头运费及运费税，逐订单只计一次 |
| `paid_fee_net` / `paid_fee_tax` | 同 cohort 明确费用行及其税额；不可假设费用总为 0，来源不存在该项须有明确零值证据 |
| `paid_order_total` | 同 cohort 源订单总额；逐单须等于上述商品、税、运费和费用六项之和；不平即数据质量失败，不制造调平项 |
| `refund_count` / `refunded_order_count` | occurred_at 在 B 的 distinct refund_id 数及 distinct 关联 order_id 数，与支付 cohort 独立 |
| `refund_amount` | 当日退款记录归一化非负金额之和，含纯金额/跨期退款；不从退款状态或商品金额反推，不再从 paid_product_net 扣一次 |
| `average_paid_order_value` | `paid_order_total / paid_order_count`；分母为 0 返回 null + `ZERO_DENOMINATOR`，不可返回 0 或 Infinity |

订单头、行和退款 ID 同源唯一；完全相同的分页重复也须作为采集异常处理，不能掩盖分页不稳定。
支付证据以 source 的规范 paid_at 为准，completed_at/status 不补造 paid_at；缺 paid_at 不计支付，
单列 created_at 在 B 且 paid_at=null 的 `orders_without_payment_timestamp`，展示“未记录支付时间”，不能声称这些订单均未支付。
已识别状态与 paid_at 冲突列为质量问题，由冻结来源映射规则判断可用性；未知插件状态默认阻止完整报告。
`paid_at`/退款记录仅表示平台记录，不证明支付网关实际到账、结算或退款成功；UI 文案必须保留该限制。
金额均为采集时观测的源订单组成，不承诺历史支付瞬间金额不可变；更新导致复核不一致则 incomplete。

退款 quantity_known/restock_known 原样保留；纯金额退款未知件数不能填 0，不从金额推件数、回库或库存修改。
完整空数据：各 count/amount 为 0，均值 null。来源失败：metrics 为 null、`complete=false`，不能伪装空日。
平均值另带精确 numerator/denominator；展示值按币种精度 HALF_EVEN 量化（当前支持币种 JPY=0，其余=2），
舍入只发生在 display，原金额、比值和 hash 不丢精度。v1 不额外展示易混淆的“净收入/现金流/利润”。

### 2.3 确定性异常规则

`daily-rules-v1` 输入只接受已验证事实和版本化显式配置，LLM 不设阈值或计算异常。
先交付数据完整性/金额不平/支付时间缺失等质量 finding，以及 `NO_RECORDED_PAYMENTS` 信息提示。
业务异常可支持 `LOW_PAID_TOTAL`（paid_order_total < 显式绝对阈值）和 `HIGH_REFUND_AMOUNT`
（refund_amount > 显式绝对阈值），严格等值不触发；阈值币种须等于报告币种且非负。
未配置则 disabled 并显示 `RULE_NOT_CONFIGURED`，不编造店铺阈值、不称已完成业务异常验收。
跨日涨跌和退款率暂不定义，避免把跨期退款金额除以同日支付额误称同 cohort 退款率。
每个 finding 持久化 code/severity、rule_version/config_hash、事实引用及参数；质量阻断不允许人工豁免。

## 3. 来源/快照/报告不可变绑定与迁移提案

版本分别固定为 `p6-daily-source-v1`、`p6-daily-snapshot-v1`、`p6-daily-report-v1`、
workflow `p6-daily-report-v1`、task kind `daily_report`；不扩写旧 commerce-v1/库存 schema 的含义。
新来源注册需绑定组织/店铺、adapter/environment、外部店铺键、币种/时区、config_ref/version、
覆盖策略、容量/总截止、金额字段/状态映射版本、不可变凭据引用和非秘密 config_digest。
沿用 M2 私有 pin 原则，秘密字节及其 hash 不进公开 DTO/日志/DB；不得从旧 D 锚七日绑定推定日报能力。

任务创建、采集和提交前逐次核当前授权及服务器实际配置与登记 digest，客户端不能登记或提供实际 URL。
轮换不改写旧报告；任务的原绑定失效时 `needs_attention`，不自动改绑新版本、重采或回填旧期。
每个 snapshot 冻结 source_binding_id/version/digest、source_kind/fixture_version、business_day、
UTC 窗口、币种/时区、采集起止、coverage、complete、quality、规范订单头/行/退款证据及 content_hash。
report 冻结 snapshot_id/content_hash、metric/rule/config 版本、全部 facts/findings 与 facts_hash。
canonical 使用现有排序/Decimal/UTC/null 编码；集合按稳定 ID 排序；hash 覆盖版本与来源，不含 LLM 文案。
报告追问/推送均引用此同一组 ID/hash，不能以当前“最新报告”替换。

**待 Root 协调的 schema 提案**：在当前 head 后单一迁移新增日报专用不可变 source binding、snapshot、report，
及 schedules、schedule_runs、report_deliveries、report_questions 的窄表；具体 DDL/ACL 须先独审。
证据允许单个有界 canonical JSON + 关键索引/FK，首片不建通用订单同步仓库或重复数据湖。
复用 business_tasks/jobs/outbox/audit_events，不松旧库存 schema、once、保护列或历史来源触发器。
关键复合 FK 绑定同 organization/shop/task；`UNIQUE(task_id)` 固定一份 snapshot/report，
`UNIQUE(schedule_id,due_at)` 固定一期，`UNIQUE(report_id,destination_binding_id)` 固定投递意图。
runtime 无来源登记权限；证据 append-only，schedules 仅窄启停/版本 CAS，run/delivery 仅窄状态更新。
报告写入与 task completed/投递意图须同事务，失败回滚；重放核原报告 hash，不再采集覆盖证据。
本轮不新增迁移文件、根配置、锁或 CI；这只是提案，不构成实施放行。

## 4. 同 Worker 持久调度、去重和恢复

调度记录由有店铺 scope 的 admin 配置，运行 owner 另须当前 operator；admin 不自动获得业务读取权。
v1 仅每日一期；配置包含稳定 schedule_id、不可变 schedule_version、owner/conversation/source/rule 绑定、
启用状态及 first_due_at。due_at 定义为业务日结束的当地午夜换 UTC，再加配置的非负 elapsed delay_minutes
（0–1439）；它是日界线后延迟，非任意 cron/固定当地墙钟。UI 必须说明 DST 时差，不能虚称每日固定墙钟。
first_due_at 及延迟必须显式配置，不给未确认的真实店铺默认推送时刻。

扫描放入现有 Worker maintenance，仅在同 runner 无在途 Graph 时执行，周期上限沿用 ≤30s。
以 DB UTC now 计算到期；每个 schedule 事务内行锁，核当前 owner/来源/配置；无权则暂停并审计，不能换操作者。
原子插入 run + business_task + analyze job + 审计，job dedupe 绑定 schedule_id/due_at；
run 保存当期 schedule_version/business_day/实际 due_at，不依赖内存 timer 或 checkpoint 去重。
已存在 run 返回同 task/report；两个扫描竞争、事务失败和进程重启不得新增第二期任务。

停机错过多期时，只新建 **now 前最近一期且 ≥first_due_at**，记录错过期数及边界，不逐日补全历史。
之前已经创建但未完成的 run 仍逐个按原队列恢复，不因“补最近”删除或换绑；同一期失败不换新 key 重建。
Worker 忙导致 actual_started_at 晚于 due_at，分别记录排队/调度延迟，不冒充准点执行。
运行只用原 analyze/recover job、原单 runner/version 注册和终止确认 gate；lease 到期不是接管授权。
提交后 checkpoint/ACK 丢失，先读业务 report/run 回执；存储失败使用原有有界重试，不能重跑已提交报告。
启停/配置变化与创建一期在同事务锁内线性化；已入队但未采集的停用 run 不执行/推送，保留可审取消原因。
改时区、延迟或接收对象必须产生新 schedule_version 并显式指定未来 first_due_at；旧 run 仍绑定原版本，
未开始的旧 run 取消，已开始者提交前再次核版本，不符则停为 needs_attention，不发布或投递部分结果。
已保存报告保持可读；停用、版本变化或撤权阻止尚未外发的投递。已进入 sending 的在途请求不能承诺撤回，
按真实回执记 sent/unknown 并保留配置变化时间；禁止另向新目的地重发旧期。旧任务/旧版本不能被新配置复活。

## 5. 受控投递与 unknown

报告保存时生成唯一 outbox + report_delivery 意图，目的地引用服务端已登记、已授权的 destination binding。
初始默认 `sender_enabled=false`，仅本地 fake sender；外部实际发送另须 Root 具体对象/窗口授权。
发送前重新核 owner 权限、schedule enabled/version、来源与 report/snapshot/facts hash、目标绑定及原 gate。
目的地不能来自模型/追问/客户端自由 chat_id；不伪造原 P4 inbox/WS 来源，不挪用旧 IM once 或窗口。

payload 为程序生成的日期、币种、指标、完整性、报告引用/链接，附 source/evidence 标签；无客户资料。
冻结完整 payload/hash、report/facts 引用、目的地绑定/版本和 provider key；发送时逐项复核，不以最新配置替换。
复用 outbox 的持久 provider key，在网络前提交 sending/attempt；成功记录 external_id/真实回执。
发送返回前崩溃或结果不明标 unknown，不回 pending、不换 key/正文/目的地自动重试；**不盲重发**。
仅经已验证同 key 去重能力或只读对账明确后处理，
不能仅凭重启/checkpoint/exactly-once 宣称外部只发送一次。报告已完成与 delivery failed/unknown 分开显示。
不完整来源仅显示质量诊断；不得发送带部分全天指标的“正常日报”。

## 6. 报告证据追问

追问显式绑定 task_id/report_id/snapshot_id/content_hash/facts_hash，不猜群聊上一份或别人的报告。
v1 问题种类为 `metric_definition / metric_evidence / finding_reason / data_quality`，携带相应 metric_key/finding_id；
不支持的自由分析返回 `clarify/unsupported`，不自动转动态工具、补货或业务写流程。
证据来自该 report 的冻结 snapshot，不发起新 commerce 采集，不把不同时点数据拼成原报告。

引用 DTO 至少有 evidence_id、snapshot_id、entity_kind（order/refund/metric/quality）、脱敏 entity_ref、field_path；
每条答复 claim 必须引用存在的证据/指标。分页最多 50 条，返回 count/next_cursor；完整聚合由服务端预计算，
展示前 50 条不称全部依据。无客户姓名/地址/邮件、原始平台 body、配置路径或凭据。
数值和公式从确定性事实插入；未知支付时间/退款数量/采集覆盖只能明确说明不足，不补编原因。

相同 actor + report/facts_hash + 规范问题 + request_key 原子返回原 question task；同键不同正文 409。
Worker 内执行、持久结果先于 checkpoint/ACK；GET 只读缓存，不启动模型或采集。
初片采用可复核模板并标 `narrative_mode=template/evidence_mode=not_used`；后续模型只整理允许 claim，
须另冻 prompt/model/预算/usage、逐引用验证及降级测试；本轮不继承 P204 旧实际 provider 预算或 key。

## 7. API DTO、权限与最小 UI 边界

以下均为**拟议新合同，尚无端点**。采用现有 `/api/v1` session envelope、身份、Origin/CSRF、
auth_version/revocation、组织与店铺 scope；内层 `schema_version=p6-m3-web-v1`，DTO strict/extra=forbid。
每次 API/Worker/发送均重新授权。日报仅 owner 的 operator 可读/创建/追问；其他用户不可见返回 404；
approver/admin 角色不自动继承日报 owner 业务权限。schedule 管理由显式 admin+operator 的同 owner 操作。

| 操作 | 请求 / 响应核心 |
|---|---|
| `GET /api/v1/daily-capabilities?shop_id=...` | `enabled/source_kind/source_config_version/earliest_business_day/metric_version/question_kinds`；来源无效 enabled=false，不能回退 Mock |
| `POST /api/v1/daily-reports` | shop_id、business_day（可省略）、capability 的 source_config_version、UUID request_key；202 返回 task_id/state；同 actor/endpoint/key 相同正文返回原 task，冲突409 |
| `GET /api/v1/daily-reports/{task_id}` | task state/failure_code，未 ready 时 report=null；ready 时下述 report，不为轮询创建任务或外发 |
| `POST /api/v1/daily-reports/{task_id}/questions` | report/snapshot/content/facts 引用、kind/metric_key或finding_id、UUID request_key；202 返回 question_id/state |
| `GET /api/v1/daily-reports/{task_id}/questions/{question_id}` | state/answer/claims/citations/evidence_mode；未完成 answer=null |
| `GET /api/v1/daily-reports/{task_id}/evidence?report_id=...&cursor=...` | 同 report 显式绑定的脱敏证据页；cursor签名绑定 actor/org/shop/report/hash，失效不自动换最新 |

report 包含完整 §3 引用、business_day/window/timezone/currency、source/evidence/consistency、
collection_started_at/collected_at、complete/quality、metrics/display/findings、rule_config 状态，
以及 schedule_run（可空）和 delivery（disabled/pending/sending/sent/failed/unknown）。
完整报告 metrics 不为空；质量失败诊断 metrics=null；不能把 queued/failed/null 当 0。
实际 schedule 配置/启停先由受控 owner CLI 提案，不开放 UI 自由配置目的地或复杂管理面板。

错误保持固定 safe_message、trace_id 与安全 code：401 `IDENTITY_REQUIRED`、403 `SCOPE_DENIED/CSRF_INVALID`、
404 `RESOURCE_NOT_FOUND`、409 `REQUEST_KEY_CONFLICT/SOURCE_VERSION_CHANGED/REPORT_NOT_READY/REPORT_BINDING_MISMATCH`、
422 `INVALID_REQUEST/UNSUPPORTED_BUSINESS_DAY`、503 `SERVICE_UNAVAILABLE`。
已排队来源错误作为 task failure_code（`DAILY_SOURCE_INCOMPLETE/DAILY_SOURCE_UNAVAILABLE/DAILY_PERMISSION_INVALID`），
不把失败变为202成功报告；GET该任务本身可200返回失败态。上游原错误/URL/SQL不暴露。

Web 最小消费仅日报日期/来源、指标和口径、完整性/异常、加载与失败、明确 report 绑定的四类追问及证据分页；
保留模板/Mock/真实标签和 delivery unknown。不接库存审批 DTO、不显示退款/支付动作或“已到账”。
Web 只能使用后端已提交且独审冻结的 DTO/OpenAPI/金标，不能把本草案端点当已可调用。
