范围依据：[PRD](../PRD.md)、[ROADMAP](../ROADMAP.md)、[ARCHITECTURE](../ARCHITECTURE.md)、[DATA_MODEL](../DATA_MODEL.md)、[AGENT_DESIGN](../AGENT_DESIGN.md)、[FEISHU_INTEGRATION](../FEISHU_INTEGRATION.md)、[STATUS](../STATUS.md)。合同版本 `0.2.1-c1-revision`；完整产品提案见 [C1方案](c1-product-design.md)。页面、角色与异常已形成规格，C1修订已通过用户产品评审；B1a视觉已通过，本次B1b已获授权并在同文件增量交付；B2/B3未授权，当前证据见[B1b](c2-b1b-delivery.md)。

先把任务、报告、审批、内部工作项和轨迹的用户旅程确定，再连接 Penpot 原型，最后由 Phase 3–4 的负责人实现 Next.js。Penpot 是视觉基线，结构化规范是行为基线。静态截图、原型跳转和自动生成的 HTML/CSS 都不能代替可鉴权、可恢复的业务实现。

## 1. 事实与动作

- 每个报告展示来源 `mock/test`、销量窗口的起止和店铺时区、库存观测时点、规则与计划版本、完整性和假设。最近七天为七个完整自然日；当前日不纳入销量。
- 数值来自确定性事实；LLM 解释和模板降级有不同标识。未知库存、Token 或费用显示“未知”，不显示为 0；空数据与失败分开。
- 分析任务状态、审批历史决定、内部补货项生命周期和同步状态分开显示。例如内部完成且同步失败，不能改成“补货失败”或再次创建。
- 批准后显示“审批意见已记录/处理中”；最终业务回执到达后才显示内部创建完成。完成/关闭只表示内部跟进，不表示采购、付款或到货。
- 单 Worker/全局单 Graph 下区分排队、运行和等待审批；等待审批不占执行槽。轨迹展示业务证据和恢复结果，不展示思维链、秘密或未经脱敏的回调。

## 2. 身份与假设确认

operator 可以创建分析、查看授权任务和提出重算。approver 可以批准/拒绝同店铺计划，并填写原因后完成/关闭一个 open 内部工作项。admin 配置允许用户、规则与集成并处理异常，只有显式兼任 approver 后才有业务审批权。无权限身份展示清楚的访问限制，隐藏按钮不是服务端鉴权证据；Web/API/飞书共用授权合同。

在途未知保留原始 null，草案注明按 0 估算及重复补货风险，逐项列明所有受影响 SKU。只提供“确认在途未知按 0 估算并批准本版本”和“拒绝此假设并拒绝计划”，分别对应 `approve_with_assumptions`、`reject_assumptions`。确认键须与冻结计划完全匹配，并绑定 plan_id/version/hash；不能用普通批准、默认勾选或关闭弹窗代替。缺库存数量、分页不完整等硬错误不能被人工确认豁免。

同操作者、同版本、相同有效动作的重复点击显示既有决定；相反动作、其他操作者或不同确认集合显示冲突，不能回滚历史决定。已生效决定的重复查询不再次执行，即使后续过期也只返回原结果。新版本、数量/范围/假设变化需要重新审批，旧确认不继承。默认最多 20 个可执行条目，超出先缩小范围，不能隐藏条目后批准。

## 3. 异常与可访问性

加载、空结果、未登录、过期会话、权限撤销、审批过期、计划变化、数据不完整、模型说明降级、429/超时、同步失败和外部结果未知各有独立状态。恢复沿用原任务和幂等键；重新分析明确产生新版本。未知外部写入结果先对账，UI 不给出会盲目重发的普通重试。

C1已规定、C2仍须实测键盘导航、可见焦点、弹窗 focus trap/返回触发器、错误文本关联、颜色以外的状态标识和飞书窄屏可读性。本次 Penpot POC 只验证鼠标原型，不声称这些已通过。

## 4. 稳定 ID 与变更流程

screen/control/event 分别使用 `M1-S* / M1-B* / M1-E*`，飞书为 `M1-F*`，弹窗为 `M1-M*`；测试使用独立 `POC-*`。改名不改语义 ID；删除要保留 superseded 记录。每个可操作节点的图层名称和 `commerceops-ux` shared plugin data 存稳定 ID/revision，结构化规范记录 file/page/shape UUID。角色从服务端取得，画布标记不提供授权。

变更按以下顺序交付：

1. 需求/Issue 指明受影响的屏幕、角色、状态和业务合同；金额、权限、幂等变化先交领域负责人。
2. 修改产品规范，再更新 Penpot 视觉和 Prototype；冻结原生版本，回读 UUID/交互并更新映射与截图。
3. 同一 PR 更新 screens/interactions/tokens/acceptance 和版本映射，附实际证据；未映射或未点击验证保持 pending。
4. Phase 3–4 的 Next.js 实现读取这些文件，组件/路由映射稳定 ID，使用 `data-testid` 等便于定位；不机械采用生成的 HTML/CSS。
5. Playwright 验证导航、弹窗、角色拒绝、过期/冲突/失败，业务集成测试核对 T3/T4/T6；视觉和行为各自附结果。失败、skipped、Mock 和真实飞书分别记录。
6. 外部审核及用户明确合并确认后才进入 main。基线清单绑定设计版本、合同 commit、实现 commit 和测试 run；设计合入不自动通过 M1 Gate。

[竞品官方研究](c1-research.md)已完成文档核实，借鉴具体问题入口、上下文解释、可查看口径与动作范围；不照搬自动批准、预测采购、通用BI或全渠道业务。

## 5. 外部评审后的设计决定

- 三个主入口及任务内报告/轨迹结构已接受；D06采用T2自动送审，报告页只导航查看审批。
- D01按最小权限设计，兼任只合并各角色在自身scope内的授权；共同拒绝条件优先，不拼接动作权与其他角色scope，admin不自动有业务读/审批权。后端落实pending BC01。
- D02：Web提交前参数澄清仅为草稿；飞书关联具体任务异步澄清。预解析、关联/去重/持久化/续跑均pending BC02，不新增后端状态/API。
- D03：待执行计划重算、拒绝/过期后重新发起、completed新周期分开；旧计划/审批/确认不可复用，具体迁移/API待BC03。新周期只开草稿并显式创建新task。
- D04不启用通用手动恢复。B09只保留ID，不渲染；自动恢复和安全对账沿用已有合同。
- D05–D08保持只读管理、自动送审、实际期限展示、无额外报告导出。D09按主闭环、身份异常、辅助/待协议交互分批，组件复用；见 [批次计划](c2-batches.md)。
- S04窄屏/F01完整展示全部SKU与风险后再提供最终动作；不全/截断/版本不一致则不批准，不能以普通批准或Web链接绕过披露，平台回退pending BC06。
- 已接受产品决定、后端pending、原型实测、业务实现分别标注。完整 [决策记录](c1-decisions.md) 是本轮修订依据；B1a视觉已通过，本次B1b已获授权；B2/B3仍须另行授权。POC保留；design-tokens追加独立M1候选区，不覆盖POC值。
