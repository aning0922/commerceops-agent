## 1. 产品主张与范围

CommerceOps 是帮助运营把一次库存问题推进到可追溯内部工作项的操作台。首页以“有哪些任务需要关注、下一步由谁处理”为中心；对话负责表达意图和解释，报告负责呈现证据，审批负责授权，工作项负责后续跟进。

M1 使用 MockCommerce，接入真实飞书审批与 Base 投影；界面持续标注“Mock 数据 / 内部工作项”。包含任务、冻结报告、版本绑定审批、单项完成/关闭、执行轨迹和必要访问/异常界面。不增加真实采购、入库、供应商、Woo 写入、BI 看板编辑器、日报调度、动态任意查数、RAG 或多 Agent。

依据：[PRD §2–6](../PRD.md)、[ROADMAP M1/Phase 3–4](../ROADMAP.md)、[DATA_MODEL §2–5](../DATA_MODEL.md)、[AGENT_DESIGN §1–5](../AGENT_DESIGN.md)、[FEISHU_INTEGRATION §3–5](../FEISHU_INTEGRATION.md)。这些是产品合同依据，不依据旧文档的阶段状态描述推断当前 Phase 1 Gate 是否通过。

## 2. 信息架构与交互模式

三个主导航为 **任务中心、审批、内部补货**。报告和执行轨迹属于具体任务的上下文页；管理员入口置于侧栏底部。保留原草案 ID，新增任务概览、审批列表和工作项详情。列表与详情属于同一模块，不把每个状态做成独立产品功能。

| 导航/层级 | 页面 ID | 用户要解决的问题 |
|---|---|---|
| 任务中心 | S02 → M02 新建分析 → S09 任务概览 | 发起请求、了解当前状态、找到下一步 |
| 任务详情子导航 | S09 概览 / S03 报告 / S06 执行轨迹 | 结果是什么、依据是什么、系统做过什么 |
| 审批 | S10 审批列表 → S04 审批详情 | 我能处理哪个版本、批准范围是什么 |
| 内部补货 | S05 列表 → S11 详情 → M01 原因弹窗 | 已创建哪些内部工作项、谁在何时完成/关闭 |
| 辅助入口 | S01 登录 / S07 访问限制 / S08 管理说明 | 进入授权范围、解释拒绝、定位运行问题 |
| 上下文辅助层 | M03 口径 / M04 报告解释 / M05 重算预览 | 不离开事实上下文理解数字与版本变化 |
| 飞书入口 | F01 审批卡片 → S04/S09 | 在协作渠道决策、回到 Web 跟踪 |

表内 ID 均带 `M1-` 前缀。拟议 URL、父子关系和深链规则见 [sitemap](sitemap.md)。全局没有“聊天历史”第二套任务列表；自然语言请求归入任务，解释面板绑定 task_id/report_id。只读筛选、排序和展开不会修改冻结计划或批准范围。

### 全局页面骨架

桌面左侧稳定导航，顶部为页面标题、店铺、环境、当前身份/角色及账号菜单。详情页保留面包屑与任务编号；标题下显示**业务状态、审批决定、同步状态**三个独立区域。主体优先事实和需要处理的异常，次级解释按需展开。每页只有一个当前主要动作；审批的显式确认与拒绝是并列决策，不藏在“更多”中。

列表返回时保留筛选/页码/滚动位置；深链先鉴权再加载数据。身份切换清空旧身份缓存。页签切换不取消已受理任务；关闭浏览器不取消服务端任务。刷新恢复服务端事实，不恢复未提交的审批决定。M1 不设计撤销任务、删除历史或自动重试所有失败的一键操作。

## 3. 完整用户旅程

### J01 · 从自然语言到内部工作项

| 步骤/页面 | 用户看到与操作 | 服务端事实与下一步 |
|---|---|---|
| 1 S01 → S02 | operator 登录，看到 Mock 店铺、本人有权查看的任务；点击“新建库存分析”B10 | 身份来自会话；无权限身份去 S07 |
| 2 M02 | 输入“分析最近七天的销量和库存，找出缺货风险并生成补货建议”；显示默认七个完整自然日、店铺时区、商品范围、演示规则参数 | 文本不是授权。常规请求直接提交；缺参/歧义的接续合同见 D02，不能伪造任务新状态 |
| 3 M02 → S09 | B01“创建分析并按规则送审”；旁注“有可执行建议时自动生成审批请求，批准前不创建内部工作项” | T1 成功才返回编号，`queued`；响应未知用原 request_id 查询/重试，不换键新建 |
| 4 S09/S06 | 显示排队、采集、校验、计算、说明、准备审批的实际步骤；可离开页面 | 单 Worker 串行，排队与运行耗时分开；无依据不显示百分比/精确排位/预计完成时间 |
| 5 S03 | 查看结果摘要、全部 SKU 事实、风险与执行资格、来源/完整性、版本；B18 查看口径，B19 解释本报告 | 数值由确定性计算；解释失败可使用模板。无建议直接 completed/no_action；硬质量问题不得生成可执行假象 |
| 6 S03 → S04/F01 | 有有效建议时显示“审批请求已生成”，B17“查看审批”；没有第二个有副作用的“提交审批”按钮 | T2 保存冻结计划、pending approval、blocked outbox；可恢复中断持久化后开放卡片发送。发送失败不抹掉审批记录 |
| 7 S04/F01 | approver 看完全部 ≤20 个条目、期限与假设；已知在途用 B02/B05，未知在途用 B03/B04 | 一次点击 T3 保存决定+完整确认集合+resume job。接受未知估算不能改写 raw null，也不能豁免其他硬错误 |
| 8 S04/S09 | 显示“审批意见已记录，等待执行复核”；没有立即出现“补货成功” | Worker 再校验权限、版本、期限、完整新鲜数据与 open 项；通过才 T4 全部创建，否则需重批/处理 |
| 9 S09 → S05/S11 | 显示“内部工作项已创建 N 项”，单独显示 Base 同步中/失败/未知；逐项查看来源 | T4 回执是内部结果。同步失败只恢复投影；不能重建已存在的工作项 |
| 10 S11 → M01 | 同店铺 approver 选择完成或关闭，填写原因，B07/B08 提交 | T6 按 expected_version/request_key 更新单个 open 项。显示操作者/时间/原因；原任务仍 completed，不代表到货 |
| 11 S02/M02 | 下一周期需要时由 operator 新建分析 | 新 task、snapshot、plan、approval；旧 execution 不重放生成下一批 |

示例只用演示数据：SKU-A 最近七天原始需求 70 件、退款件数独立展示；D=10、A=20、L=3/R=7/S=2、目标120、风险线50、可靠在途0时 Q=100。若在途未知，同样的100仅是按0估算草案。界面不标为实际预测、采购量或已确认在途为零。

### J02 · 澄清、零结果与不完整数据

商品名称歧义时显示原句、候选 SKU、当前解析范围和需要补充的一项信息。不得猜选首个商品；超20可执行条目要求缩小范围，不通过筛选隐藏后批准。PRD 支持澄清，但现有任务状态/HTTP 合同没有澄清续答端点：D02 是 C2 阻塞决策；在确认前只画可评审草案，不声称已经具备会话续答能力。

“完整查询、没有销量/风险”展示空结果解释与窗口；“数据缺失/分页失败”展示不完整标识、失败来源与不可执行原因；“未生成报告”展示当前阶段而非空表。未知库存用“未知 + 原因”，负库存保留负号；D=0 不制造覆盖天数或补货量。数据不足形成说明报告也不等于正常无风险，是否结束 task 或 needs_attention 由服务端结果决定，前端不自行推导。

### J03 · 拒绝、过期、并发与计划变化

拒绝后显示已决定人与时间、被拒版本和零内部工作项；没有撤销批准按钮。过期 pending 只能看历史并由有权 operator 提出重算。新版本、在途事实/假设变化、库存池冲突或权限撤销在执行前阻止创建，显示具体原因与最新版本入口。历史 approved 不改成 rejected；页面把“历史批准决定”与“当前计划不可执行”同时呈现。

同人同版本相同有效动作重复返回既有结果；另一个人、相反动作或不同集合显示冲突，先读服务端事实，不提示不停重试。即使原决定之后已过期，合法重复查询仍只展示历史回执。关闭卡片/弹窗没有决定效果。

### J04 · 响应丢失与外部同步异常

审批/完成工作项提交超时显示“提交结果待核实”，锁住相反动作，先刷新原对象。允许安全重投时沿用同一键与 payload，不能换键或重置版本。业务任务 completed + sync_failed 显示“内部已完成，飞书同步待恢复”；sync_unknown 显示“外部结果待对账”，无普通重发按钮。管理员在 S08 查看脱敏异常和既有维护说明；M1 不增加后台 shell、任意重跑或对账授权 API。

### J05 · 飞书与 Web 同一决定

授权私聊/群 @ 创建任务返回任务编号。卡片列全量批准范围及未知假设，批准后先 Toast“审批意见已记录/处理中”，最终结果异步更新。Web 和飞书并发点击服从同一个 T3 合同。卡片转发不授予权限；共享卡片不能按阅读者隐藏敏感信息，因此应仅发既有允许范围。Web 深链仍需登录且重验 scope，不把 URL 或卡片当作会话凭据。实际客户端兼容和20条窄屏布局留待 C2/Phase 4 验证。

## 4. 角色与可见性提案

下表“授权范围”须由服务端校验组织、店铺、对象可见性；**读范围细则 D01 待确认，C1 不授予新权限**。建议 operator 默认仅本人任务及其派生对象；approver 仅 eligible 的审批关联任务及已有 PRD 允许的同店铺内部工作项；admin 仅脱敏配置/异常元信息，业务数据还需显式业务读权限或兼任角色。

| 内容/动作 | operator | approver | admin 单角色 | 无权限身份 |
|---|---|---|---|---|
| 任务中心/报告/任务轨迹 | 授权任务可读 | 授权审批关联任务可读 | 无默认业务读权；仅异常元信息 | 不加载业务数据 |
| 新建分析/提出重算 | 允许；重算目标仍需对象授权 | 兼任 operator 才允许 | 兼任 operator 才允许 | 禁止 |
| 审批记录查看 | 授权任务只读 | 同店铺且 eligible | 无默认业务读权 | 禁止 |
| 批准/拒绝 | 兼任 approver 才允许 | 当前角色、eligible、版本/期限均有效才允许 | 不自动获得 | 禁止 |
| 内部工作项查看 | 本人授权任务派生项，待 D01 | 同店铺，待 D01 读范围确认 | 无默认业务读权 | 禁止 |
| 完成/关闭单项 | 兼任 approver 才允许 | 同店铺 open + 原因 | 兼任 approver 才允许 | 禁止 |
| 安全恢复任务 | D04 确认前入口禁用并说明 | 同左；不能因审批权自动获得 | 现有维护流程；不新增 Web 写入口 | 禁止 |
| 配置与异常说明 | 无入口 | 无入口 | 只读摘要与维护说明；配置写 UI 另议 D05 | 禁止 |

角色可兼任，显示真实角色标签但不提供“切换角色即获权”的演示开关。列表计数必须使用同一授权范围，不能由全店总数泄露其他人的任务。无权 deep link 与不存在对象采用同一安全提示，不显示标题、SKU 或审批人。权限在页面打开后撤销时隐藏旧敏感内容并进入 S07，副作用必须服务端再次鉴权。

## 5. 状态与关键交互矩阵

| 事实层 | 状态及呈现 | 用户可继续做什么 |
|---|---|---|
| 分析任务 | queued 排队 / analyzing 分析 / awaiting_approval 待审批 / executing 复核执行 / completed 内部完成或无动作 | 看进度、报告、审批、派生项；按上下文导航 |
| 分析异常/终态 | rejected 已拒绝 / expired 已过期 / needs_reapproval 需重新审批 / failed 失败 / needs_attention 需处理 | 查看原因；有权提出重算；恢复须 D04 合同 |
| 审批 | pending / approved / rejected / expired / superseded | pending且授权才有决策；历史决定只读 |
| 内部工作项 | open / completed / closed | 仅 open 可完成/关闭，原因必填 |
| 投影 | pending / synced / failed / unknown | 看最近同步时间/版本/错误；unknown 先对账 |
| UI 局部 | loading / empty / submitting / result_unknown / conflict / stale / forbidden | 不写成业务枚举；以对象最新事实收敛 |

|---|---|---|

| E02/B02 普通批准 | S04/F01 → 当前审批结果 | 仅无required_assumptions；完整冻结范围；T3不代表T4完成 |

| E06/B06 提出重算 | S03 → M05 | 先列变化与旧确认不继承；提交语义由D03确认 |
| E36/B36 确认重算 | M05 → S09 | 新不可变版本/新审批；已完成任务下一周期新task；API待领域负责人确认 |

完整控件清单见 [interactions.yaml](interactions.yaml)。跨屏共用的语义控件沿用同一 ID，C2 给每个画布实例单独 UUID；事件实例映射不能只保存一个主按钮而漏掉飞书按钮。

## 6. 视觉、可访问性与文案建议

采用中性浅底、白色内容面、深色正文、少量青绿色主动作；告警用琥珀色，错误用红色，成功用绿色并始终带文字/图标。沿用 [POC 设计值](design-tokens.json) 作为候选，不把 POC 字面色值宣称为 M1 已批准 token。避免渐变背景、过大数字卡、装饰图表、拟人化“思考中”动画。

桌面参考宽1440，侧栏约216–232，内容边距24，区域间距24，表格行44–48；主要文字14–16，页面标题24，二级标题18，辅助文字不低于12–13。中文用可本地打包的字体方案或系统字体；确切字体包与授权在 C2 核对。表格数值右对齐、单位进列头、等宽数字；长SKU支持换行/展开和复制可见标识，不截断唯一身份。

报告默认显示 SKU、风险、原始需求、可用库存、原始/估算在途、建议量、资格/阻断原因；日均需求、退款、覆盖天数、参数等在行详情/口径面板。默认排序按风险严重度再SKU，筛选计数明确“当前显示/全部范围”。审批页不沿用筛选来隐藏批准条目：最多20条完整列出，任何数据未加载完时禁用决策。

低于1024的详情页辅助栏下移；约390宽的飞书入口/Web审批纵向卡片列出每个SKU，动作按钮可多行，风险说明与完整批准范围不隐藏。大数据表可水平滚动并固定SKU列；不以无限滚动代替批准范围。C2优先验证1440任务/报告、390审批和原因弹窗，桌面/窄屏具体布局尚未实测。

键盘顺序按阅读顺序；焦点可见，弹窗聚焦标题/首个字段、限制焦点并回到触发器；Esc关闭不产生决定。危险/授权动作不绑定全局Enter，表单中Enter不跳过披露。输入错误在字段旁且与读屏关联；提交结果用适度live region，轮询不抢焦点。目标为正文对比度≥4.5:1、关键非文本边界≥3:1、触控区域≥44px，**这些是验收目标，尚未测试**。

文案使用“内部工作项已创建”“内部跟进完成”“外部结果待核实”；不使用“采购成功”“库存已补足”。Token未知显示“未返回”，费用注明估算与价格版本。等待审批期间不显示忙碌百分比；无内容时给出原因和一个符合权限的下一步。

## 8. C1交接、C2闸门与工具缺口

本方案仅更新 docs/ux。结构化清单保持 `planned_unmapped`、`penpot=null`；新增 `design_status=review_required`。POC画布、MCP、Compose、evidence、token文件维持原样。C1文档审阅通过不等于C2原型通过或M1业务完成。

C2在用户明确授权后，先按J01做任务/报告/审批/内部项关键链，再覆盖J02–J05及角色异常。每个Board、控件和状态变体写稳定ID与合同版本；保存独立M1视觉revision并回读UUID。全部业务状态不必各做独立整页，但必须有可定位的变体与可点击路径；每个交互实例记录 source/target UUID。用户评审前不执行此批次。

Phase 3–4实现前读取本合同、已批准Penpot版本、决策记录；将screen/control/event映射到路由、组件、data-testid。变更按“业务需求与合同 → 结构化UX → Penpot → 代码 → Playwright/领域测试”同步，同PR说明遗漏与延期；T3/T4/T6必须另外验真实业务事务，不能用原型代替。

**独立记录的工具缺口（本轮不处理）：** 原生 `.penpot` API导出失败；官方UI下载未取得可核查归档；私有PG+assets备份未做异机/新卷恢复。已有原生快照/同卷重建恢复不能替代便携归档与灾备。原始证据继续见 [A/B验收](acceptance.md)；C2前用户知悉风险，后续单列基础设施任务，不在C1修Penpot源码或自建MCP。
