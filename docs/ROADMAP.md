# 分阶段路线图与外部配置

状态：2026-10-08 架构评审稿。Phase 0 之后暂停；以下是计划，不表示已获准开始开发。P0/P1/P2 是业务优先级，Phase 0–6 是开发阶段，两者不要混淆。

## 1. 推荐实现顺序

| 阶段 | 依赖 | 独立交付 | 验收门槛 | 粗略工作量 |
|---|---|---|---|---|
| Phase 0 调研设计 | 当前授权 | 十份核心设计、调研证据、AGENTS/README | 用户评审范围/状态/权限边界 | 本轮完成 |
| Phase 1 工程底座与技术探针 | 架构通过；Docker daemon；外部配置用于真测 | uv/Node 锁、PG migration、最小任务/Worker、checkpointer crash probe、飞书消息/卡片/Base probe | PG 持久队列与中断恢复验证；锁定 SDK 兼容；真机探针证据或明确外部阻塞 | 3–5 工作日 |
| Phase 2 确定性库存垂直切片 | Phase 1 本地底座 | Mock fixtures、统一契约、快照、规则、API 报告、模型受限说明 | 金标完全一致；空/异常/分页失败不产生错误执行计划 | 3–4 工作日 |
| Phase 3 审批与恢复闭环 | Phase 2；Phase 1 图恢复结论 | approval、graph interrupt/resume、内部补货、outbox、最小 Web 审批/轨迹 | 拒绝/重复/并发/重启/提交后崩溃不变量通过 | 5–7 工作日 |
| Phase 4 飞书正式闭环与 Woo 只读 | Phase 3；测试组织和测试店 | 飞书卡片、Bitable 投影、Woo adapter、身份联调 | AC01 飞书全链路；Woo 两页以上真实数据和金额/时区/退款核验 | 5–7 工作日 |
| Phase 5 P0 稳定与作品交付 | Phase 4 | 完整 Compose、恢复/备份手册、测试证据、录屏、架构说明 | AC01–09、干净启动、关键故障演示；用户能解释关键取舍 | 3–5 工作日 |
| Phase 6 P1 扩展 | P0 验收后新授权 | 先日报/追问/定时，再 SOP RAG/文案草稿 | 日报指标金标、定时去重；引用和审核草稿闭环 | 额外 10–15 工作日 |

P0 预计 19–28 个有效工作日，含基础测试，不包含账号审核、网络问题和用户验收等待；这是按一位主要执行者的任务拆分估算，不是固定交付承诺。阶段结束更新估算。不要把整个项目压成“几天写一个 Agent”。

飞书技术探针提前至 Phase 1，避免最后才发现卡片投递或权限问题。账号等待期间可完成 Phase 1 本地部分和 Phase 2，但不能把缺失的飞书闸门默认为通过。Phase 3 的设计不得绕过尚未验证的 checkpoint 并发边界。

## 2. 每阶段验收证据

- Phase 1：版本锁与环境说明；真实 PG probe 的命令/结果；中断后进程终止再恢复；飞书 SDK 版本及脱敏投递样例。尚缺账号时写清 pending 项。
- Phase 2：fixture manifest、黄金计算结果、已知异常列表、一次真实模型说明及一次受控失败降级。
- Phase 3：R01/R05/R07/R08/R11/R12/R17 的数据库断言和轨迹；Web 刷新不丢任务。
- Phase 4：真实飞书私聊/群 @ 录屏或截图；批准/拒绝；Bitable 行回读；Woo 后台与 API 金额/数量对账。
- Phase 5：从空环境按 README 完成离线演示，真实集成按配置启用；备份还原后待审批任务继续；不存在密钥和旧项目绝对路径依赖。

用户需要在阶段评审决定继续。GitHub 仓库、推送及 PR 已按后续协作要求授权，遵循 [AGENTS.md](../AGENTS.md)；合并 main 仍须用户确认。云部署与扩大平台权限另需用户授权，不因本地功能可用就自动发布。

## 4. 风险与处理顺序

| 优先级 | 风险 | 缓解 / 验收阻断 |
|---|---|---|
| 高 | 审批状态、图进度、外部副作用不存在天然统一事务 | 业务唯一键+短事务+outbox+恢复协调；关键 crash tests 是门槛 |
| 高 | 飞书测试组织权限/长连接新版卡片实际投递未知 | Phase 1 真机探针；必要时受鉴权 HTTP 回调，不能静默跳过卡片验收 |
| 高 | Woo 数据语义/共享库存/退款与模拟数据不同 | 契约测试、实际样本对账、质量闸门；只读测试店 |
| 中 | PG 自建队列变成第二个通用任务框架 | 只支持少量 job kinds；不做插件调度/复杂 DAG；若恢复实现持续失控再评估成熟队列 |
| 中 | 模型编造数字或“已执行” | 程序渲染数值、结构化引用、业务状态模板、工具写权限隔离 |
| 中 | 外部幂等键保留期限不足 | PG 长期回执、外部稳定业务 ID 对账、unknown 人工处理 |
| 中 | 本机 Node 20 生命周期、版本快速变化、Docker 未启动 | 项目容器 Node 24 LTS；版本兼容 probe；不改全局环境 |
| 中 | 前端/RAG 挤占可靠性工作 | Web 极简；RAG/pgvector 放 P1；无报表大屏需求 |
| 中 | 本地电脑休眠影响接收/定时 | 明确在线窗口；持久 job 补偿；有全天需求时另评部署 |

## 5. 架构评审需确认的取舍

推荐接受：P0 只创建内部补货任务；Woo 只读；PG 队列与独立 Worker；新版卡片长连接；pgvector/RAG 延至 P1；一名审批人即可作决定（名单可多人，先有效决定生效）；计划变更必须重批；20 条审批上限超出要缩小范围。

业务待定：真实补货提前期/复查期/安全天数、在途信息来源、是否要求发起人与审批人分离、单次预算。设计默认值足以继续离线实现，正式业务验收前需要用户确认。若要求审批后直接采购或变更库存，这是重大范围变化，需新的权限和接口设计。

**Phase 0 结束即暂停，等待架构评审；本轮不安装业务依赖、不创建测试应用、不发消息、不接真实店、不开始 Phase 1。**
